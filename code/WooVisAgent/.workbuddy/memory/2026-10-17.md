# 2026-10-17

## 视频生成功能（文生视频 + 图生视频）

在图片生成的异步架构上新增视频生成，复用同一套链路：提交 → RabbitMQ → Worker 生成 → SignalR 推送。

### 架构决策（用户确认）

1. **新建独立 `WooVisAgentServices.VideoService` 项目**（而非塞进已有 3766 行的 ImageService）。
2. **协议必须通用、与平台无关**——用户明确要求"用户配置的模型都能用，只要兼容 OpenAI 协议都可以"，因此否掉了"每厂商一个协议类"的方案，改为**预设 + 可配置模板**。
3. **ffmpeg 抽帧做封面**，缺失时优雅降级（不生成封面、时长留空，视频本身仍成功）。
4. **轮询上限 15 分钟**。
5. **模型配置里显式声明能力**（supportsTextToVideo / supportsImageToVideo），前端隐藏不适用输入 + 后端提交前强校验。

### 关键事实：视频接口没有事实标准

与图片有 OpenAI Images 标准不同，视频生成各家差异贯穿全链路，实测：

| | 提交路径 | 轮询 | 任务号 | 状态 | 产物 |
|---|---|---|---|---|---|
| OpenAI Sora | POST /v1/videos | GET /v1/videos/{id} | `id` | `completed` | **二进制** GET .../content |
| 阿里云百炼 | POST .../aigc/video-generation/video-synthesis | GET /api/v1/tasks/{id} | `output.task_id` | `SUCCEEDED` | URL `output.video_url`（24h 过期）|
| SiliconFlow | POST /v1/video/submit | **POST** /v1/video/status + body | `requestId` | `Succeed` | `results.videos[0].url` |

百炼文生与图生视频**共用同一路径**，靠 model 名区分（t2v/i2v）；首帧字段是 `input.img_url`（不是 image_url）。

### 测试暴露并修复的 3 个真实 bug

1. **endpoint 双前缀**：`https://xxx.aliyuncs.com/api/v1` + `/api/v1/services/...` → `.../api/v1/api/v1/...`（404 且报错误导）。改为 `VideoDeliverySpec.Combine` 消除重复前缀。
2. **SiliconFlow 被误判成百炼**：其模型名 `Wan-AI/Wan2.2-T2V-A14B` 含 "wan"，而原推断把百炼判断放在最前。改为**主机名优先**，模型名只作兜底。
3. **分辨率档位按高度判断**：竖屏 720x1280 被判成 1080P。改为看**短边**。

### 其他实现要点

- `GenerationTaskDispatcher` 改为按 `Task.Type` 分派——因为 `RetryGenerationTask` 是类型无关的通用用例，视频重试也走它。
- `TaskProgressPump` 与进度类型（`GenerationProgress`）提到类型无关层供图片/视频共用，删掉了原本图片专属的 `ImageGenerationProgress`。
- `VideoGenerationRequestedFactory` 放在 EventBus：视频消息有**两个**构造点（提交用例 + 重试用例），收敛到一处防漂移。
- ModelConfig 新增 `DeliveryJson` / `SupportsTextToVideo` / `SupportsImageToVideo` 三列——**无需迁移**，既有 `EnsureMissingColumnsAsync` 会自动补列。

### 验证

## 追加：ffmpeg 路径配置化 + 真实二进制验证

用户要求"下载 exe、配置路径就用它生成封面，不配置就按现在方式降级"。

### 配置方式（已实现）

`WooVisAgent.GenerateWorker/appsettings.json` 的 `VideoMedia` 节点，或环境变量 `VideoMedia__FfmpegPath`（容器部署更方便）。
支持完整路径或裸命令名（走 PATH）。带引号的路径会自动剥引号（Windows 复制粘贴常见）。

### 顺带修掉的 4 个真实 bug

前 2 个是配置化过程中发现的逻辑缺陷，后 2 个是**只有用真实 ffmpeg 跑才暴露**的：

1. **可用性探测靠猜**：原 `CheckExists` 是"路径带分隔符就 File.Exists，否则一律 true"。默认配置 `ffmpeg` + 机器没装时误报可用 → 每条任务启动进程才失败，最该出现的"请配置路径"提示反而看不到。改为**真的执行一次 `-version`**。
2. **static 缓存探测结论**：`_availabilityChecked` 做成 static，导致第一个配置的结论被之后所有实例共享（换配置后仍是上一个的结论）。改为实例字段 + `Lock`。
3. **`RunAsync` 先读流后启动**：`process.StandardOutput` 在 `Start()` 之前访问会抛异常，而异常被上层 catch 吞掉 → **ffmpeg 明明可用，封面与时长却永远为空**，日志只留一条 Warning，排查方向被带偏。这是本次最隐蔽也最严重的一个。
4. **`format.duration` 是字符串不是数字**：ffprobe 输出 `"3.000000"`，`ReadDouble` 只认 `JsonValueKind.Number` → 时长恒为 null，表现为"分辨率有、时长没有"。改为同时解析字符串。

### 测试策略（值得沿用）

- `VideoMediaInspectorTests`：用**假 exe** 覆盖配置解析 / 引号剥离 / 实例隔离 / 不可用时安静降级，断言的是 `IsAvailable` 而非处理结果——因为"没装 ffmpeg"和"装了但文件有问题"在处理返回值上都是 null，区分不出来。
- `FfmpegIntegrationTests`：环境变量 `VIDEO_MEDIA_TEST_FFMPEG` 指向真实 ffmpeg 时才运行（否则跳过，避免没装 ffmpeg 的机器红灯），断言**时长 3s / 分辨率 640x360 / 封面是有效 JPEG**。
- **验证测试本身有效性**：把修复临时回退成旧逻辑，确认测试真的变红，再恢复。否则容易写出一堆"永远通过"的假测试（本次就发生过一次）。

### 实测结论

下载 ffmpeg 9.0.2 实测：配好路径后时长 3s、分辨率 640x360、封面成功抽出，全部正确。
测试总数 117（新增 10 条 ffmpeg 相关），**配置与不配置 ffmpeg 两种环境下均 117/117 通过**。

> 注：本环境下载 ffmpeg 包多次被截断，用 `curl -C -` 断点续传才拿到完整包——若后续要在 CI 里准备 ffmpeg，注意这个坑。

## 追加：修复启动报错 23502（补列失败）

用户启动报 `Npgsql.PostgresException: 23502: column "DeliveryJson" ... contains null values`。

### 根因

项目不用 EF Migration，靠启动时三段式自建表（`InitializeDatabaseAsync`：EnsureCreated → EnsureMissingTables → EnsureMissingColumns）。
我给 `ModelConfig` 加 `DeliveryJson`（非空字符串）时，**只在 C# 属性上写了 `= "{}"` 就以为有默认值了**。

但 **C# 属性初始值不会进入 EF 元数据**。补列逻辑读不到默认值，于是发出
`ALTER TABLE model_configs ADD COLUMN "DeliveryJson" text NOT NULL`（无 DEFAULT）→ 存量 4 行立即 23502 → 服务起不来。

### 修复

1. `ModelConfigConfiguration` 显式配 `HasDefaultValue("{}") / (true) / (true)`（照抄 `GenerationTaskConfiguration` 里 `IsSelected` 的正确范例）。
2. `BuildAddColumnDefinition` 增加防护：必填列若没有数据库默认值，**直接抛带指引的异常**而不是发必然报错的 SQL——原来的 23502 只有表名列名，完全看不出"是这条字段没配默认值"，排查会被带偏。

### 防护自身踩的坑（已修）

第一版防护放在 `BuildModelColumns` 里**为整张表预生成所有列定义**，结果 `OwnerId` 等早已存在的历史必填列（本就无 DB 默认值）也被校验，误报成
"OwnerId 是必填列却没有默认值"，**连没有新增列时都让启动失败**。

改成**只在确认某列真的缺失时才生成定义并校验**（`BuildModelColumnMap` 返回 IProperty，循环内再调 `BuildAddColumnDefinition`）。

### 顺带发现的既有坑

`ExecuteSqlRawAsync` 内部走 `string.Format`，默认值 `'{}'` 被当格式占位符 → `FormatException: Expected an ASCII digit`。
项目里早有 `ExecuteNonFormattedSqlAsync` 专门规避；我写测试时又踩了一次。查询侧 `SqlQueryRaw` 同样如此——本项目 `GenerateCreateScript` 不解析的注释也是同一原因。

### 测试

- `SchemaEvolutionTests`：元数据层断言「必填列必须有 DB 默认值」，并附**历史豁免白名单**（项目里本来就有 22 个这类列，不豁免会长期红灯）。另有一条断言白名单不能膨胀。
- `SchemaMigrationLiveTests`：**连真实 PostgreSQL** 跑完整闭环——先手工执行无 DEFAULT 的语句确认确实 23502（证明场景被覆盖），再用带 DEFAULT 的语句补列并断言存量行被正确回填为 `{}`；跑完自动删列恢复现场。没连接串时跳过。

> 该测试一开始我试图直接调 `InitializeDatabaseAsync`，被 Identity 的 `RoleManager` 依赖卡住；改为直接执行等价 DDL 即可验证同一件事，不引入无关依赖。

### 实测

对着用户真实数据库（Aspire postgres 容器，4 条模型配置）验证：旧语句确实报 23502，新语句成功且 4 行全部回填为 `{}` + 双能力 true，与用户已配置的百炼模型兼容。测完已把列删除还原（恢复为 14 列）。

测试总数 122，**有无真实库两种环境下均 122/122 通过**；Release 编译 0 错误。

## 追加：修复两个前端 bug（视频模式选不到模型 / 作品筛选无效）

用户报两个现象，都是"点了没反应"型问题。

### Bug 1：聊天窗口切到视频后，模型下拉仍是图片模型

根因不止一处——视频链路**整条都没接**，下拉只是症状：

1. `availableModels` 之前写死 `modelStore.imageModels`，切 mode 列表纹丝不动 → 挑不到任何视频模型。
2. `send()` 里 `if (mode === 'video') { message.info('还在接入中'); return }` 直接短路，压根不提交。
3. `ChatCard.payload` 是图片专属结构，视频参数（时长/帧率/分辨率/音效）无处安放。

改法：模型列表按 mode 取对应分类；新增 `submitVideo()` 接 `POST /api/video/generations`；卡片按 `kind` 分流（视频走 `VideoPlayer`，`<img>` 渲染 mp4 只会是破图标）；补时长/帧率/音效三个下拉；`fetchVideoTask` / `cancelVideoTask` 按卡片类型分流轮询与取消（两个 Controller 都复用同一批通用用例，结构一致）。

**顺带修掉一个交叉类型隐患**：原 `submitVideo` 里 `?? currentModel.value` 会回退到**图片模型**（重跑旧视频卡时当前 mode 是图片），把图片模型 id 发给视频接口必被后端「该模型不是视频模型」拒掉。两边都改成**只在各自分类内回退**，且实际使用的 `modelId` 以解析结果为准，保证「卡片显示的模型 / 重跑 / 提交」三者一致。

### Bug 2：作品库点图片/视频筛选没反应

**后端与筛选逻辑都是对的**（`GetMaterialAssetsQuery` 只认 image/video，其余值忽略），问题在前端：

```ts
const materials = materialStore.materials   // ← setup 那一刻的快照
```

store 内部 `materials.value = result.items` 换的是 **store 的引用**，局部变量仍指向旧数组。

之所以表现为"还是显示所有"而不是"数据不动"：工作台（`WorkspaceView`）用的是 `computed(() => materialStore.materials)`，**已经把 store 填过了**。作品库页面 setup 时快照到的正是那份数据，所以看着"全是"；点筛选后 store 换成新数组，页面还指着旧的。

改法：改用 `storeToRefs` 解构 `loading / materials / total / groups`。

> 这类"响应式丢失"排查有个通用判据：**先确认另一处有没有用 computed 访问同一个 store**。有 computed 的页面数据会动，没快照的页面不动，对比即可定位。另外解构 store 时 `storeToRefs` 是安全写法，`const x = store.x` 只对 getter 有用、对 state 会退化成快照。

### 验证

`vue-tsc --noEmit` 通过，`vite build` 通过。
