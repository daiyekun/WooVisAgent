# 2026-10-18

## 视频生成卡死在 22% 的排查与修复

现象：任务 `369875133164158976`（Video）停在 Running / 22%，18 分钟无任何进展，既不成功也不失败。
经查数据库确认状态，`netstat` 显示无任何 dotnet 进程持有 443 连接——**不是网络挂起**。

### 根因（多个缺陷叠加）

1. **`VideoDeliveryFramework.PollUntilCompletedAsync` 缺 CancelAfter**
   图片侧 `ModelDeliveryFramework` 第 845 行有 `timeout.CancelAfter(PollTimeout)`，
   视频侧是照着抄的但漏了这一手。deadline 检查写在循环末尾，
   一次请求挂起就永远走不到；而 `HttpClient.Timeout` 是 20 分钟 > 轮询窗口 15 分钟，
   于是窗口形同虚设。

2. **`TaskProgressPump.ApplyAsync` 抛异常会静默杀死泵**
   异常被塞进 `pumpTask`，要等生成结束 `await` 时才浮出水面。
   视频动辄几分钟，这段时间用户看到的就是彻底静止的进度条（停在 22% 的直接原因）。

3. **消费者幂等保护无超时兜底**
   `Running && StartedAt != null → 跳过`。执行体一死，后续每次重投都被跳过，
   任务再也不会有进展也不会失败。这是"永不收敛"的放大器。

### 修复

- `VideoDeliveryFramework`：轮询窗口挂 linked CTS + `CancelAfter`；
  新增 `RequestTimeout`（90s，public 以便测试断言）套在每次请求上，
  单次超时只记日志继续等（偶发抖动不该耗尽窗口）；
  `MaxPollMinutes` 15 → 20；`HttpClient.Timeout` 20min → 25min（仍须 > 窗口与弹性管道 5min）
- `TaskProgressPump`：`ApplyAsync` 失败只记日志，泵继续活着；新增可选 ILogger
- `VideoGenerationRequestedConsumer`：Running 但心跳超时（窗口+5min）则接管重跑；
  MarkFailed 失败时记 Critical
- **新增 `StaleTaskReaper`**（Worker 后台服务，每 2 分钟扫描）：
  把 Running/Queued/Pending 且心跳超阈值的任务收敛为 Failed 并推送前端。
  阈值由 `MaxPollMinutes + 5` 推导，避免改一处忘一处。
- 前端：进度区新增跳秒的「已等待 Xm Ys」+ 视频等待预期说明（`.gl-hint`）

### 验证

- `dotnet build` 0 错误；**全量测试 129/129 通过**（新增 2 条：单次请求超时 < 轮询窗口 等）
- **实测生效**：重启 Worker 后，那条卡死任务在 16:27:19 被清扫器判为 Failed，
  前端立刻可见，用户可直接重跑

### 踩坑记录

- `StaleTaskReaper.BuildReason` 最初传实体，但调用方已先把它改成 Failed，
  导致两种原因都落到兜底分支。改为传 `GenerationTaskStatus` 参数。
- 既有测试 `轮询上限必须小于HttpClient超时` 把 HttpClient 超时**硬编码成 20 分钟**，
  改注册处的值后断言就失真了。应像同文件另一个用例那样从 `IHttpClientFactory`
  实际装配出的 client 上读超时——验证装配结果，不在测试里抄字面量。

  重启前应先确认旧进程已停干净，否则跑的可能是旧代码。

## 视频卡在 23% 的真正根因：Wolverine 默认消息执行超时 60 秒

上一次判定为"轮询缺 CancelAfter / 进度泵异常"，都改对了，但用户重启后仍卡在 23%。
这次查运行日志与数据库，证据链闭合，根因是**消息框架层**：

- `WolverineOptions.DefaultExecutionTimeout` 默认 **60 秒**（包 XML 注释可查）。
  `WooVisAgent.EventBus/DependencyInjection.cs` 的 `UseWolverine` 从没配过它。
- 视频轮询窗口是 20 分钟。实测任务 `369887382020816896`：Handle 00:40:26.987 →
  00:41:27.094 抛出 `TaskCanceledException`，**恰好 60.1 秒**，栈在
  `VideoDeliveryFramework.cs:400`（`Task.Delay(PollInterval, cancellationToken)`）。
- 进度 23 = `20 + 70 × (58.3s / 1200s)`，即第 2 次轮询上报后 2 秒被砍。
- 消费者的 `catch (OperationCanceledException) when (cancellationToken.IsCancellationRequested)`
  把框架超时**误判成服务停止** → 保留 Running 并 rethrow → 消息进死信队列 → 再没人管，
  最后只能等 `StaleTaskReaper`（25 分钟）兜底。所以用户正好等了 25 分钟。
- 历史日志 10-17 15:52 有完全相同的栈（任务 `369875133164158976`），**不是偶发，是必现**。
- 副作用：Worker 死后模型侧仍在生成，出片无人下载，白扣费。

### 修复

1. `EventBus.DependencyInjection` 新增 `DefaultMessageExecutionTimeout = 30 分钟` 并设进 `opts`；
   公开为常量以便测试断言。文档注释写明"必须 > 视频轮询窗口并留收尾余量"。
2. 两个消费者注入 `IHostApplicationLifetime`，用 `ApplicationStopping.IsCancellationRequested`
   区分"真关停"（保留 Running 并 rethrow）与"框架超时"（`MarkFailedAsync` 落可读错误）。
   回写终态必须用 `CancellationToken.None`——原 token 已取消。
3. 图片消费者同病（轮询窗口 3 分钟也 > 60 秒），一并修。
4. `MaxPollMinutes` 的"改动要同步三处"注释改为四处（含 EventBus 超时）。

### 教训（值得记住的排查判据）

- **进度条卡在固定百分比时，先比对"卡住的耗时"**：60.1 秒这种与框架默认值精确吻合的数字，
  比"某个百分比"更能定位。22% / 23% 只是巧合，两次不同的窗口长度会算出不同的数字。
- 把 `cancellationToken.IsCancellationRequested` 当作"服务停止"的信号是不成立的：
  框架超时、上层取消都会置位。要判关停就用 `IHostApplicationLifetime`。

### 作品库里的视频是黑框、点不动

  就去掉工具重试一次。`Agent:EnableToolCalling` 可整体关掉。

### 踩坑：qwen-plus 的 JSON 输出极不稳定（这条最重要）

实测三种包裹，全部会导致「整段 JSON 被当成提示词填进输入框」或「参数全空」：
1. 整段 JSON 被再包一层字符串字面量 `"{\"a\":1}"`；
2. 整段结构被塞进字段里 `{"polished":"{\"polished\":\"...\"}"}`；
3. **长中文里夹未转义字符，整段 JSON 非法**（`JsonDocument.Parse` 直接失败，但字段本身是完整的）。

第 3 条是最后才定位到的：直接调网关是干净 JSON，线上偶发失败，靠加日志抓原文才看清。
结论：**不要用「整段 JSON 必须合法」作为解析前提**。`AgentJson` 现在按 `"key"` 定位逐字段取值
（`ExtractString` / `ExtractInt` / `ExtractStringArray`），`Unwrap` 负责拆嵌套，JSON 合法只是最顺利的一种情况。
`TryParseObject` 仍保留给需要结构化校验的场景与测试用。
